# Design

## Context

Мотивация описана в `proposal.md`, поведение — в `specs/employee-selection/spec.md`.

`src/components/App.tsx` получает конфигурацию и операции через `useSimulator`, хранит `userId` и `serviceId` локально и строит полный список сотрудников из `config.users`. Результат запрашивается через `checkAccess`, когда оба идентификатора непустые. Проверки существования выбранных записей после импорта сейчас нет.

Модель уже содержит `User.groupIds` и `Config.groups`. `calculateAccess` учитывает все группы сотрудника. Импорт через `src/app/index.ts` заменяет конфигурацию целиком только после успешной проверки; при ошибке состояние конфигурации сохраняется. Существующие спецификации расчёта и импорта этому изменению не противоречат.

Компоненты получают данные и типы только из `src/app`; конфигурация остаётся в браузере. Новая логика выбора не требует изменений домена или хранилища.

## Goals / Non-Goals

**Goals:**

- Держать состояние выбора согласованным с текущими вариантами полей до показа результата, включая замену конфигурации.
- Оставить единственный источник списка сотрудников — актуальную конфигурацию; получать отфильтрованный список как производное значение.
- Проверить поведение через действия пользователя на экране и настоящий слой приложения.

**Non-Goals:**

- Менять публичный интерфейс `Simulator`, структуру `Config` или алгоритм `calculateAccess`.
- Добавлять общее хранилище состояния интерфейса, сохранение фильтра или отдельную подсистему поиска.
- Менять форму выдачи разрешений и жизненный цикл её внутренних полей.

## Decisions

### 1. Локальный фильтр экрана

В `App` добавить выбранный `groupId`; пустая строка обозначает «Все группы», как пустые значения существующих полей. Список групп строить из `config.groups`, сотрудников — из `config.users` с проверкой `groupIds.includes(groupId)`. Отбор по массиву сотрудников сохраняет порядок и не размножает сотрудника при повторе членства.

Альтернатива — хранить фильтр в `useSimulator` или `Config`. Она расширяет контракт приложения и формат данных ради временного состояния одного экрана. Отдельный список отфильтрованных сотрудников в состоянии также не нужен: его пришлось бы синхронизировать с конфигурацией.

### 2. Явное согласование выбранных идентификаторов

При смене группы вычислить новый список и в том же переходе сбросить сотрудника, если он в него не входит. Сервис сохранить. Не выбирать первого участника автоматически.

При изменении конфигурации согласовать состояние в порядке: существование группы, видимые сотрудники, существование выбранного сотрудника в видимом списке, существование сервиса. Отсутствующая группа превращается в «Все группы»; отсутствующий или исключённый сотрудник сбрасывается; отсутствующий сервис сбрасывается. Сохранившиеся идентификаторы остаются выбранными, имена и результат берутся из новых данных. Неуспешный импорт не меняет конфигурацию и выбор.

Согласование должно обновлять само состояние выбора, чтобы сброшенный сотрудник не восстанавливался при следующем расширении списка. До согласования не показывать результат для идентификаторов, которых нет в текущих вариантах. Проверять выбранного сотрудника и сервис перед вызовом `checkAccess`, а не только непустоту строк. Не полагаться на визуальное поведение браузерного `select` при исчезновении его текущей опции.

Альтернативы: всегда сбрасывать сотрудника при смене группы или сбрасывать весь экран после любого импорта. Они теряют действительный выбор без необходимости. Только вычислять пустое значение для поля без очистки состояния тоже недостаточно: старый выбор может неожиданно вернуться.

### 3. Существующие элементы интерфейса

Использовать `NativeSelect` с доступной подписью «Группа» перед «Сотрудник», в стиле текущего экрана. Оставлять «Не выбран» в поле сотрудника. Для выбранной группы без участников показывать отдельный текст «В этой группе нет сотрудников» и стандартное приглашение проверки. Для «Все группы» это сообщение не показывать даже при пустой конфигурации.

Альтернатива — поиск по имени или множественный выбор групп. Они требуют другого взаимодействия и не нужны для исходного сценария одной команды.

### 4. Полная конфигурация для расчёта и редактирования

Передавать в существующий `checkAccess` только идентификаторы сотрудника и сервиса. Полную конфигурацию не сокращать: это сохраняет прямые источники и разрешения всех групп. `PermissionsPanel` продолжает получать исходную конфигурацию. Фильтр не вызывает операции сохранения, выдачи или отзыва; экспорт остаётся экспортом всей конфигурации.

Альтернатива — отфильтровать конфигурацию целиком. Она исказит ответ о доступе и затронет остальные панели.

### 5. Проверки через пользовательские сценарии

Реализацию вести скиллом `tdd` по `AGENTS.md`: добавлять по одному падающему сценарию, затем минимальный код и рефакторинг. Расширить `App.test.tsx`; проверки взаимодействия с импортом разместить рядом с существующими сценариями в `Permissions.test.tsx`.

Для сценария студии подготовить тестовую конфигурацию с восемью участниками «Северной», посторонним сотрудником, сотрудником без групп, участником нескольких групп и пустой группой. Загружать её через существующий формат и ключ хранилища в тесте; учебные данные приложения не менять. Проверять варианты внутри конкретного поля, поскольку имена повторяются в панели разрешений.

Проверить: состав и порядок вариантов, снятие фильтра, сохранение и сброс выбора, отсутствие восстановления сброшенного сотрудника, пустую группу, все источники доступа, неизменность панели разрешений, экспорта и хранилища, перезагрузку и успешный/ошибочный импорт с изменением групп, членства и сервисов. Использовать существующий полный прогон как регрессионную проверку домена и формата импорта; новые изолированные тесты алгоритма расчёта не нужны.

Альтернатива — тесты только функции фильтра. Они не проверяют согласованность полей и показ результата после импорта.

## Risks / Trade-offs

- Устаревший `userId` может оставить результат скрытого сотрудника или восстановиться позже → согласовывать само состояние и проверять актуальность перед расчётом; покрыть переход через чужую группу и возврат.
- Успешный импорт может удалить группу или изменить членство при тех же именах → сопоставлять записи по идентификаторам и заново строить варианты из конфигурации.
- Фильтрация конфигурации может скрыть независимый источник доступа → фильтровать только варианты сотрудника; проверить участника двух групп с прямым разрешением.
- Линейный отбор выполняется при рендере → для учебных браузерных данных достаточно обычного прохода, отдельный индекс и кеш пока не вводить.
- Фильтр сбрасывается при перезагрузке → это принятое поведение временного состояния экрана, отражённое в спецификации.

## Migration Plan

Миграция данных не требуется: версия файла, ключ хранилища и модель не меняются. Изменение поставляется обычной сборкой статического приложения. Откат интерфейса не требует преобразования сохранённой конфигурации.
